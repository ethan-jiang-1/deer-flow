# 组合模式与收尾纪律：跨原语协同

本页是 [00-map.md](00-map.md) 编排阶梯的第五篇：单原语的完成语义见 [01](01-完成语义与崩溃窗口-接受可见静止处置.md)，状态的持久/派生/内存三分见 [02](02-状态三分法-持久事实派生投影与内存权限.md)，预算叠加链见 [03](03-资源预算与公平性-并发深度总量与容量边界.md)，LangGraph 未用能力面见 [04](04-LangGraph能力面榨取-未用原语与接入设计.md)。本页回答的问题是：**原语叠起来用时会发生什么？哪些组合被结构性禁止、哪些靠运行期软化、哪些自由？一段组合工作的"扫尾"由谁、按什么顺序做？run 完成的通知走哪几条通道、丢了怎么兜底？**

一个必须先钉死的总判断：DeerFlow 的组合治理**没有中心调度者**。原语之间靠三样东西协同——工具表的**结构性剔除**（某个 run 形态直接没有某个工具）、运行期 context 的**软化开关**（工具在但行为被改写）、以及**预算归属链**（哪个 run_id 的预算被哪个原语消耗）。本页逐条核验这三样东西在各组合下的真实行为。

## 1. 组合形态清单：禁止、软化与自由

### 1.1 两套"去 clarification"机制（父侧核验，本页复读确认）

DeerFlow 有**两个不同层次**的 ask_clarification 剥夺机制，冲突矩阵里必须分开列：

**结构性剔除（non_interactive）**：lead agent 工厂在组装工具表时，`non_interactive=True` 的 run 直接把 `_NON_INTERACTIVE_DISABLED_TOOL_NAMES` 里的工具从表里过滤掉（`backend/packages/harness/deerflow/agents/lead_agent/agent.py:1059`-`1060`）——模型根本看不到 `ask_clarification` 的 schema，调用从"被拒绝"降为"不可想象"。工具表在 run 开始前定型，中途不可变。`non_interactive` 是 internal-only context 键：`_CONTEXT_INTERNAL_CALLER_KEYS` 只在请求以进程内部用户认证时合并（`backend/app/gateway/services.py:522`-`524`），`merge_run_context_overrides` 对外部调用者丢弃该键，`strip_internal_context_keys` 还会从 `body.config` 自由格式里洗掉走私副本（`backend/tests/test_gateway_services.py:3434`-`3478` 钉死两条进料口）。

**运行期软化（disable_clarification）**：工具仍在表里，但 ClarificationMiddleware 在 `after_model` 里检测 `context.get("disable_clarification")`（`backend/packages/harness/deerflow/agents/middlewares/clarification_middleware.py:388`），命中时不再走 `Command(goto=END)` 中断，而是"指示 agent 继续推进"（`clarification_middleware.py:457`）——模型生成的 ask_clarification 调用被改写成继续执行的提示。区别还体现在**兄弟工具调用**上：disable_clarification run 保留同回合的其他 tool call（`backend/tests/test_clarification_middleware.py:861`、`:938`），而普通 clarification 中断会把同回合兄弟调用一并丢弃。这个键由非交互通道（如 GitHub）在 run_context 里设置（`backend/app/channels/manager.py:1746`），同样被 `_CONTEXT_RUNTIME_ONLY_KEYS` 信任边界保护（`services.py:578`、`:584`——注释明说"disable_clarification 不是 non_interactive 的温和表亲"）。

第三处交叉：沙箱网络审批把两个键**等价对待**——`_network_approval_is_non_interactive` 检查 `disable_clarification or non_interactive`（`backend/packages/harness/deerflow/sandbox/middleware.py:40`-`41`，消费点 `:571`、`:592`）：非交互 run 的网络审批自动放行/拒绝，不再弹人。

### 1.2 逐组合核验

| 组合 | 判定 | 机制与锚点 |
|---|---|---|
| scheduler 触发的 run × ask_clarification | **结构性禁止** | 定时 launch 设 `context={"non_interactive": True, ...}`（`services.py:1831`、`:1916`）→ 工具表剔除（agent.py:1059-1060）；根 AGENTS.md scheduled-task 节明说目的是防定时任务停在无人应答的确认上 |
| IM 通道（GitHub 等非交互通道）× ask_clarification | **运行期软化** | 通道 run policy 设 `run_context["disable_clarification"]=True`（manager.py:1746），ClarificationMiddleware 转为"proceed"指令（clarification_middleware.py:457）；交互式 IM 通道（如 Feishu）不设此键，可正常问 |
| 子代理 × ask_clarification | **结构性禁止** | 内置 general-purpose/bash 子代理的 `disallowed_tools=["task","ask_clarification","present_files"]`（`subagents/builtins/general_purpose.py:67`、`bash_agent.py:47`，03 §一.4 已核验）——task 委派的深度=1 与 HITL 剥夺是同一张表 |
| 子代理 × task（再委派） | **结构性禁止（prompt+工具双保险）** | 同上 disallowed_tools；system prompt 另有 "You must NEVER attempt to call task"（general_purpose.py:29-30）。边界：custom agent 的 `allowed_subagents` 配置可重新暴露（03 §一.4 的配置责任） |
| goal 续轮 × task 委派 | **自由，但预算同源** | goal continuation 是**同一个 run_id** 内的隐藏 turn（worker.py:1361-1380 的 `_stream_once` 循环）；SubagentLimitMiddleware 的 per-run 总量按 run_id 过滤 durable ledger（`subagent_limit_middleware.py:82`-`92`、`:142`-`144`，03 已核验），所以**用户 turn + 全部续轮共享同一个 6 次委派预算**——不存在"每轮续命重置预算"。loop/token 预算同理明示"same-run goal continuations share history"（middlewares/AGENTS.md 第 29 条） |
| scheduler 触发的 run × task / batch_task | **自由** | non_interactive 只剔 ask_clarification（`_NON_INTERACTIVE_DISABLED_TOOL_NAMES`），task/batch 工具照常在表（agent.py:1057-1060）；batch 工具只要求 startup SQL submitter 已装（tools/AGENTS.md 第 26 条）。即定时任务可以扇出子代理与 durable 批次 |
| scheduler 触发的 run × goal 续轮 | **自由（易被忽视的组合）** | goal continuation 逻辑在 worker 的 run_agent 主循环里（worker.py:1361-1380），对每个 run 生效——定时 occurrence 跑在已有 active goal 的线程上时，**评估器照样跑、续轮照样注入**。这是把"时间平面"（scheduler）叠上"目标平面"（goal）的隐藏耦合点 |
| goal × ask_clarification | **结构性收敛（goal 主动让位）** | 续轮准入前检查 `_ends_on_human_input_request(messages)`：turn 以问题结尾 → 评估记 `blocker="needs_user_input"` 并 stand down，不注入续轮（worker.py:1997-2008）——goal 不会对着一个挂起的问题继续空转 |
| IM busy 线程 × 新消息 | **缓冲后放行** | fire_and_forget 通道 opt-in `buffer_followups_on_busy`：ConflictError 时进 per-thread 内存缓冲（上限裁剪），busy run 的 StreamBridge 流到 END 后 watcher 排空（manager.py:121-128、`_buffer_followup` `:1361`） |
| plan mode × todo_write / task | **同 turn 内互斥由 middleware 承担** | `is_plan_mode` 只挂 TodoListMiddleware+write_todos；task 委派不被 plan mode 结构禁止（组合行为由模型自律） |

**组合的纵深判断**：DeerFlow 的"禁止"几乎全部集中在**人机交互原语**（ask_clarification）与**委派再入**（task in task）上，且都用"工具不在表里"实现；其余组合（scheduler×task、goal×batch、IM×task……）都是自由的，靠预算归属链（03 的六层闸门）而非组合规则约束。这与 DSH 用 maxDepth 计数器+provider-managed 例外的预算式哲学不同：**DeerFlow 用能力面剔除表达"不可能"，用预算表达"太贵"，两者不混用**。

## 2. stop_reason 家族的聚合：两套互不相同的纪律

03 已列出七值（`loop_capped` / `token_capped` / `safety_capped` / `subagent_limit_capped` / `model_length_capped` / `turn_capped` / `scheduled_task_orphan_recovery`）。本节补的问题是**多个 guard 同时/先后触发时谁赢**——答案分裂成两套纪律，因为 lead run 和子代理走的是不同通道：

### 2.1 lead run：单一共享键，后写者胜（且源码自认是债）

五个 lead 侧 guard 全部直接写 `runtime.context["stop_reason"]` 这**同一个键**：loop_detection（`loop_detection_middleware.py:797`）、token_budget（`token_budget_middleware.py:314`）、safety_finish_reason（`safety_finish_reason_middleware.py:395`-`397`）、subagent_limit（`subagent_limit_middleware.py:168`）、model_length（`model_length_finish_reason_middleware.py:104`-`109`）。没有严重度排序、没有收集合并——**后触发的 guard 覆盖先触发的**。唯一的例外是 model_length：它带 `"stop_reason" not in ctx` 守卫（`model_length_finish_reason_middleware.py:107`），注释明说目的是"保留更早的 cap 原因穿越隐藏续轮"——即它是**先写者胜**的自我克制，而非优先级系统。

worker 在源码注释里承认这是已知设计债：`worker.py:1410`-`1414` 明文写着"If more guards grow stop_reason semantics, consider a publish/collect pattern … instead of each guard writing directly to the same key"。也就是说：**多 guard 冲突的裁决规则就是"谁最后写谁赢"，除了 model_length 让路**。

时间维度上还有一条刻意规则：worker 只在**首个用户可见 turn 之前**清除残留 stop_reason（`worker.py:1354`-`1359`）；续轮 turn 保留用户 turn 留下的 cap 原因——"用户 turn 撞了 cap 的 run 就是 capped 的，即使随后的隐藏 goal 评估 turn 干净地跑完"（#4176，`worker.py:1355`-`1357` 注释）。stop_reason 一旦在用户 turn 种下，goal 续轮**洗不掉**它。

### 2.2 子代理：consume_stop_reason 鸭子类型收集，先到者胜

子代理侧是另一套：TokenBudget/LoopDetection 各自维护 per-run_id 的 `_stop_reason: BoundedDict`（`token_budget_middleware.py:93`、`loop_detection_middleware.py:355`），经 `consume_stop_reason(run_id)` **弹出式**消费（`token_budget_middleware.py:114`-`124`、`loop_detection_middleware.py:449`-`462`）；executor `_aexecute` 用 `hasattr` 鸭子类型收集**所有**实现了该方法的 middleware，取**第一个非 None** 的原因（subagents/AGENTS.md「Guardrail caps & stop_reason」节钉死；新增 guard 无需改 executor）。加上 turn 轴（`GraphRecursionError` 被 `_aexecute` 专门捕获）与安全轴，子代理的聚合纪律是**先到者胜 + 弹出即消费**——与 lead 侧的后写者胜恰好相反。这是同族字段在两条执行路径上的真实分歧，审查时不可混用。

### 2.3 stop_reason 的三个下游消费者（跨原语传播）

1. **run 记录**：worker 终态化时把 `runtime.context` 里的值作为 `stop_reason=` 传给 `set_status_if_not_cancelled`（`worker.py:1415`、`:1431`）——run `success` 与 cap 原因并存（加性字段，不是状态枚举）。
2. **delegation ledger**：`extract_delegations` 从 ToolMessage 结构化元数据读 `stop_reason` 落到 entry（`delegation_ledger.py:147`-`149`），`_status_guidance` 把 capped completion 渲染成模型可读指令："hit a guardrail cap with a partial result; reuse the partial result, retry with a tighter scope, or raise the per-agent budget"（`delegation_ledger.py:62`-`64`）——**lead 复用被截断的子代理结果是知情重用**，不是误当干净结果。
3. **goal 续轮准入**：`run_stop_reason == "token_capped"` 直接触发 stand down——"续轮共享该预算，再跑一轮隐藏 turn 只会多花一次模型调用然后工具调用被剥掉"（`worker.py:2090`-`2094`）。这是 stop_reason 反向约束组合行为的唯一锚点：**预算耗尽会传染给 goal 平面**。

## 3. 收尾纪律：一段组合工作的扫尾顺序

01 已挖 run 终态十步持久化顺序与 worker finally 序列。本节补齐 01 之外的三层收尾：工具/子代理层、goal 层、ledger 层。

### 3.1 子代理层：超时与取消的安全路径

- **超时**：`run_with_timeout` 用 `asyncio.wait_for(timeout=self.config.timeout_seconds)` 包住整个 `_aexecute`（`executor.py:1872`-`1877`）；`TimeoutError` 分支做三件事——set cancel_event、`try_set_terminal(TIMED_OUT)`、**把最新工具回执快照进终态元数据**（`executor.py:1878`-`1885`）——超时的子代理仍然带着已收割的证据收尾，不是裸失败。`CancelledError` 分支对称（`executor.py:1886`-`1893`）。
- **协作式取消**：`request_cancel_background_task` 只 set cancel_event，由 `_aexecute` 在 `astream()` 迭代间隙协作检查（`executor.py:1925`-`1930` 注释明说子代理线程不能被 `Future.cancel()` 强杀）；后台取消在 `_background_tasks_lock` 外才调 `Future.cancel()`，避免完成回调重入死锁（subagents/AGENTS.md「Execution」节）。
- **注册表防僵尸**：提交失败时必须把刚注册的 execution_id 从 `_background_tasks` 弹掉，否则留下没人轮询的 PENDING 僵尸（`executor.py:1899`-`1910`）；registry 清理被钉在持久子代理循环上，免受 caller-loop 拆除牵连（subagents/AGENTS.md #5069 节）。
- **沙箱租约幂等双保险**：middleware 做正常释放，executor 在 `finally` **幂等重复释放**（01 已锚 `worker.py:1706`-`1711`；subagents/AGENTS.md #5128 节：异常/协作取消/超时三条解栈路径都不能漏 lease 或 scoped session）。
- **durable 批次取消**：用户取消立即终态化所有非终态 item 并清 lease，围栏 stale worker 的迟到完成；取消是持久优先，运行侧 renew 循环最迟 `lease_seconds/3` 观察到（01 已锚 `batch_service.py:166`-`181`、`:277`-`278`）。**批次没有 drain-to-empty 语义**——取消是围栏式的，不是排空式的。

### 3.2 goal 层：没有 wrapup，收尾=stand_down + 预算 + 清空

DeerFlow 的 goal 续轮**没有 DSH 式 wrapup 注入**（父侧核验，本页复核：goal.py 与 worker.py 的 goal 路径对 delegations ledger 零引用——`grep -c delegation runtime/goal.py` = 0）。goal 的收尾由三件事组成：

1. **满足即清空**：评估 satisfied 时在 goal 锁内以 `expected_checkpoint_id` CAS 写 `write_thread_goal(..., None)` 把 goal 从 checkpoint 清掉，然后向 bridge 发布 values（`worker.py:2061`-`2087`）；`GoalWriteConflict` 静默放弃（`:2083`-`2084`）。
2. **stand_down_reason 家族**（比 DSH wrapup 更接近"收据"的东西）：`needs_user_input`（turn 以问题结尾，`worker.py:2000`-`2008`）、`no_durable_end_of_turn`（没有持久回执，`:2010`-`2019`）、`thread_changed_after_evaluation`（评估期间用户插话/清 goal，`:2055`-`2059`）、`token_capped`（`:2090`-`2094`）、`thread_changed_before_continuation`（含防续轮计数双计的注释，`:2113`-`2128`）——全部持久化进 `last_evaluation`（`goal.py:567`-`568`）。
3. **预算闸门**（`should_continue_goal`，`goal.py:332`-`342`）：satisfied / blocker 不可续 / `continuation_count >= max_continuations` / `no_progress_count >= max_no_progress_continuations`，任一命中即止步。

**组合含义**：goal 收尾**不扫任何子代理尾**。挂在内存注册表上的进行中 task 不会因为 goal 满足而被收，durable 批次更与 goal 无耦合——收尾责任完全在 run 内（task 的 ToolMessage 必须回到 messages 通道才算收）与批次 owner（API/JSONL 侧自取）。这是与 DSH「先 job_output 再 update_goal complete」纪律的**结构性差异**：DeerFlow 的 goal 满足路径上没有任何工具可调、任何尾可扫。

### 3.3 ledger 层：终态不降级 + 有界记忆

`merge_delegations` reducer 保证**终态永不被非终态覆写**（`thread_state.py:198`、`:208`-`209`）、同 id 最新胜出但保留首见顺序与 `created_at`/`run_id`（`:212`-`215`）、超过 `_DELEGATION_LEDGER_MAX_ENTRIES` 截尾保最新（`:218`-`219`）。ledger 是 checkpoint 持久事实（02 主表），所以**跨 run 的委派史是收尾状态的唯一持久账本**——但它只记账不执行：没有"未终态 entry 的到期对账"机制，一个永远不回填的 in_progress entry 会一直挂着（内存注册表丢了就没人把它改成 failed，见 02 危险点 6 的推论）。

## 4. 通知与回调经济学：run 完成 → 谁被通知、丢了怎么兜底

run 的"完成事实"沿着**三条互不相同的通知通道**外溢，各有自己的经济学与兜底：

### 4.1 通道一：进程内 push 钩子（唯一注册者是 scheduler）

worker 终态序列里，`ctx.on_run_completed(record)` 在 finalizing barrier 清除与 `bridge.publish_end` **之前**执行（`worker.py:1635` → `:1690`-`:1691` → `:1693`），且被 `not record.ownership_lost` 门控——**丢了 lease 的 worker 无权发完成通知**（peer takeover 的 run 不会重复通知）。全仓只有一处注册这个钩子：Gateway deps 把 `scheduled_task_service.handle_run_completion` 接上（`backend/app/gateway/deps.py:766`）。钩子失败是 warning 级 non-fatal（`worker.py:1638`-`1639`）；BaseException 则被延迟到 finalization 之后重抛——"terminal hook 不得让 replacement run 卡死或让流消费者无限等"（`worker.py:1640`-`1650`）。

**通知丢失的兜底**：Gateway 死在钩子前 → occurrence 留在 running → 单实例靠启动 sweep `mark_stale_active_runs` + `cancel_stuck_once_tasks` 破坏性清扫（已成功的 run 被记为 interrupted occurrence，01 已锚 `service.py:567`-`582`），多实例靠 lease 对账（`service.py:586`-`607`）。兜底语义是**降级记账**，不是补发通知。

### 4.2 通道二：流哨兵（IM follow-up watcher 的排空触发器）

fire_and_forget 通道（GitHub）的 busy 缓冲排空靠**订阅 run 的 StreamBridge 流并等 `END_SENTINEL`**（`backend/app/channels/manager.py:1489`-`1491`）——与 SSE 消费者同一机制，不加新通道。watcher 故意不设超时（GitHub run 常跑数分钟，`manager.py:1472`-`1475`）。经济学细节：

- **批式排空**：一次只 pop ≤10 条（`FOLLOWUP_DRAIN_BATCH_SIZE`），合并成 `<followups-while-busy>` 块发一个 follow-up run；follow-up run 自己再被 watch，深积压**链式**排空而不是撑大单次输入（`manager.py:1518`-`1521` 注释 + channels/AGENTS.md #4121 节）。
- **失败兜底三层**：排空 run 自己撞 ConflictError → 整批重新入缓冲（`manager.py:1580`）；`runs.create` 失败 → requeue（`:1586`-`:1590`）；拿不到 StreamBridge → 只 warning，缓冲保留，"由本线程下一个被 watch 的 run 排空"（`:1480`-`1486`）。**缓冲永不因失败而丢**——只有溢出裁 oldest（`:1342`-`1355`，cap 20）。
- **已知边界**：缓冲与 watcher 都是 per-process 内存态，`GATEWAY_WORKERS>1` 或多 pod 下跨进程不共享（channels/AGENTS.md Scope limitation 节，与 #4120 同形）——与 02 危险点 6（`_runs` 进程私有）同族。
- **关机纪律**：`ChannelService.stop` 先关 manager 准入、watcher 被 cancel+await、worker `join_inbound` 有界排空（`manager.py:1838`-`1909`；service.py:283-311 见 01）——"已接受的消息在关机时尽量完成"。

### 4.3 通道三：轮询（MCP 通知）

MCP 后台任务不走钩子也不走哨兵：`dispatched` 后由 poller **轮询 run 终态**，`success → delivered=True`、失败退避重试、超限 dead-letter（01 已锚 `mcp_tasks/service.py:407`-`448`）。轮询的成本换来与 run 生命周期的完全解耦——run 消失也是可重试错误而非崩溃。

### 4.4 前端/SSE：不是通知通道，是投影

SSE 断线后客户端靠 run_events feed 回填（02 主表），`publish_end` 只是流的终点帧不是回执——把它算进通知经济学是常见误判。

**横向判断**：三条通道里只有钩子是 push（便宜但单点，靠 sweep 兜底）；哨兵是复用流基础设施的零成本观察（但受进程边界限制）；轮询最贵但最鲁棒。DeerFlow 没有通用的"run 完成事件总线"——每个消费原语各自选择通道并自带兜底，这是与 DSH 单一 inbox 模型的最大差异。

## 6. 跨原语收尾纪律清单（对照 DSH 六条的 DeerFlow 版）

1. **run 终态化前先收子代理**：task 的 ToolMessage 必须回到 messages 通道，run 的交付回执与终态化才有效（01 十步顺序）；没有等价的"最终答案前收 job"prompt 纪律——**收尾是结构性顺序，不是模型自觉**。
2. **goal 满足 ≠ 扫尾**：满足即 CAS 清空（worker.py:2075-2087），不碰任何在途委派/批次；goal 的收尾凭据是 `stand_down_reason` + 预算闸（goal.py:332-342），没有 wrapup 注入。
3. **stop_reason 是收尾叙述**：lead 后写者胜（model_length 让路）、子代理先到者胜（consume_stop_reason）、ledger 把 capped 渲染成"知情重用"指令（delegation_ledger.py:62-64）——三处消费不重合成一个真相。
4. **终态不降级**：ledger 的 terminal 永不被非终态覆写（thread_state.py:208-209），但**没有到期对账**——in_progress 挂永久挂。
5. **通知先于流终帧**：on_run_completed（scheduler 专属）→ finalizing barrier 清 → `publish_end`（IM watcher 触发点）（worker.py:1635→1691→1693）——push 钩子的消费者必须在 END 之前完成记账，否则与 sweep 兜底竞速。
6. **非交互形态的 HITL 债**：scheduler（剔工具）、非交互 IM（软化）、子代理（disallowed）三路剥夺各有失效面；新的挂起式原语（04 §3.1 的 interrupt 审批）必须同时接进这三条信任边界，否则定时任务挂在无人应答的 interrupt 上。
