# 状态三分法：持久事实、派生投影与内存 authority

> 本篇是 [00-map.md](00-map.md) 编排阶梯的第三块拼图（状态视角），方法论对标 DSH 仓库 `_digested/orchestration-ladder/13-持久事实派生投影与内存权限-状态三分法.md`——**学风格不搬事实**，所有结论只来自本仓库源码核验。
>
> **与既有 digest 的分工**：[../internals/persistence/](../internals/persistence/README.md) 两篇讲 checkpoint 双模式与存储后端的**机制细节**；[../observability/02-run-events-and-journal.md](../observability/02-run-events-and-journal.md) 讲事件捕获链路；[../concepts/memory/extract-queue-persist-pipeline.md](../concepts/memory/extract-queue-persist-pipeline.md) 讲记忆管线；[../concepts/subagent/dual-threadpool-and-lifecycle.md](../concepts/subagent/dual-threadpool-and-lifecycle.md) 讲双线程池。本篇不重复机制，只回答一个问题：**这份状态是持久事实、派生投影，还是内存 authority？重启 Gateway 后它会怎样？**

## 三层定义（本仓库版）

| 层 | 判据 | 生命周期 | 重启后 |
|----|------|----------|--------|
| **持久事实** | 落在 sqlite/postgres 表、checkpointer 库、磁盘文件（markdown/JSONL/上传目录），写入有事务或原子替换保证 | 跨进程、跨崩溃 | 原样读回；由各自的恢复/对账逻辑重新解释 |
| **派生投影** | 从持久事实**纯函数重算**，不需要失效协议（或失效只是数据生命周期而非正确性） | 进程内或共享缓存 | 冷重建；投影不单独成为新事实的来源 |
| **内存 authority** | 只存在于进程堆内，**决定当前操作的资格**（准入、互斥、取消、续租、执行权） | 当前进程 incarnation | 丢弃并重建；不能从"持久行存在"直接推导执行授权 |

判定一个字段时问四个问题：① 它进不进 durable storage？② 它从哪些事实重算？③ 哪个进程对象持有当前 authority？④ 重启后是恢复、重算、重新授权，还是标错/丢失？DeerFlow 的一个鲜明特征是：**很多"看起来像持久状态"的东西（running 状态、launching 认领、run 注册表）重启后一律走"标错/丢弃"而不是"恢复执行"**——恢复语义是 fail-closed 的账务对账，不是断点续传。

## 各层深挖

### 1. Checkpoint：唯一的"真能恢复"的持久事实

整个系统里唯一支持**跨重启继续执行**的状态是 LangGraph checkpoint 链：resume 走图执行、rollback/compaction 走 `build_state_mutation_graph` 整块替换。但三个边界必须钉住：

- **后端决定它到底持不持久**：`database.backend=memory`（开发默认）下 InMemorySaver 重启即空——"checkpoint 是持久事实"这个命题以配置为前提（[db-checkpointer-store-backends.md](../internals/persistence/db-checkpointer-store-backends.md)）。
- **mode 是进程冻结的编译期事实**：`full`/`delta` 编译进每个图的 channel 表，跨进程必须同值；full 进程读 delta thread 会 fail-closed 抛 `CheckpointModeMismatchError` 而不是返回残缺 state（[checkpoint-dual-mode-and-history-cache.md](../internals/persistence/checkpoint-dual-mode-and-history-cache.md)）。
- **delta 历史缓存是教科书级的派生投影**：条目按键 `(thread, ns, checkpoint_id, channel)` 不可变——"一个 checkpoint 的 delta 历史是其已封闭祖先链的纯函数"（`runtime/checkpointer/cached_saver.py` 模块 docstring），因此**永不需要失效协议**；`adelete_thread` 是数据生命周期 API（GDPR 式擦除）而非正确性 API。这是全仓最干净的三分法样本：事实（checkpoint 行）→ 投影（历史缓存）→ 权限（进程冻结值）互不越界。

### 2. Runs：持久行是账本，不是执行

`runs` 表行的 `status=running` 是**已写入的持久事实**，但"谁在执行"的 authority 在 `RunManager._runs` + worker 任务里（`manager.py:266`）。两者重启后的对账语义是**单向标错**：

```
重启 → _runs 清空 → 心跳停止 → lease 过期（NULL lease 也算）
     → peer 或自己启动时 reconcile_orphaned_inflight_runs()
     → claim_for_takeover 原子认领 → status=error, stop_reason=orphan_recovered
```

`reconcile_orphaned_inflight_runs` 的 docstring 写明：lease 过期的 pending/running 行意味着 owner 崩溃或被分区，**认领并标 error，绝不尝试续跑**（`manager.py:1861`-`1945`；`ORPHAN_RECOVERY_STOP_REASON = "orphan_recovered"`，`manager.py:39`）。接管顺序也有讲究：先原子 claim 再补零交付 receipt，防 stale 扫描覆盖活 run 的详细 receipt（`manager.py:1934`-`1940`）。thread 的图状态在 checkpoint 里，用户的恢复路径是**重新发起 run**（resume/重新输入），不是系统自动续传。

进程内注册表的语义同样精确：`_runs` 只持有**本 worker 准入**的记录；跨 worker 幂等复用返回 `store_only` 行**不注册**——peer 永远不会去 finalize 或 cleanup 别人的 run（runtime/AGENTS.md 钉死，测试 `test_multi_worker_run_ownership.py`）。

### 3. Journal 与 run_events：捕获缓冲是内存 authority，落库行才是事实

`RunJournal` 的三分法拆解：

- **内存 authority**：`_buffer`（< `flush_threshold=20` 条的写缓冲）、token 累加器、LLM 响应 staging（`journal.py:260`-`288`）。它们在 run 进行中是唯一的真相来源（进度、token 分桶），崩溃即丢。
- **持久事实**：flush 到 `RunEventStore` 的行。注意**事实性取决于后端配置**：`run_events.backend` 默认 `memory`——默认部署下这条"持久事实"其实是内存的，重启后消息 feed 全空（只有 checkpoint 里的 messages 还在）。db/jsonl 才是真持久。
- **派生投影**：`get_message_seqs`/`stamp_messages_with_seq` 做的 feed-seq 回填——把 checkpoint 消息与 feed seq 对齐的只读桥接，不写回 checkpoint。

**journal 是投影还是持久事实？** 答案是"都不是/都是一半"：`RunJournal` 对象本身是 run 生命周期的内存 authority（buffer + 回调簿记），它 `flush` 出去的 `run_events` 行是不可变追加的持久事实。**重放 run_events 能重建什么？** 能重建 UI 消息 feed、trace 视图、subagent 步骤卡片、token 汇总（已 flush 的部分）；**不能**重建图执行状态（那在 checkpoint）、未 flush 的尾部事件、以及内存 token 计数的最后增量。

### 4. Scheduler：队列是事实，认领是 fence

`scheduled_task_runs` 的状态机是三分法的教学案例：

| 状态 | 类别 | 重启后 |
|------|------|--------|
| `queued` 行 | 持久事实 | 存活，`_drain_queue` 继续消费（`service.py:68`）；`scheduler.queue_timeout_seconds` 限制等待时长 |
| `launching` + lease | 持久事实行 + 内存 authority（`_lease_owner`） | 过期认领被 `recover_expired_launch_claims` 退回 `queued`（`service.py:63`）；单实例启动时 `mark_stale_active_runs` 直接标 `interrupted`（`service.py:567`，错误串 `_RESTART_RECOVERY_ERROR`，`:23`） |
| `running`（引用 durable run） | 持久事实（指针） | 依赖 run 侧的 orphan 对账；`once` 任务由 `cancel_stuck_once_tasks` 收尾（`service.py:577`） |

`_lease_owner = f"{hostname}:{uuid4().hex}"`（`service.py:40`）是纯内存身份，每进程新生成——旧进程的 launch 写会被 `expected_lease_owner` fence 拒绝。启动清扫只放在 `start()` 里而不敢放进 `run_once()`，因为 lifespan await `start()` 期间不可能有本进程准入的 run（`service.py:561`-`565` 注释）。

### 5. 内存管线：队列与 watermark 都是内存 authority，且明码标价

DeerMem 的提取链把"丢得起"的部分显式放进内存：

- 队列 docstring 直说：**"process-local in-memory list plus a debounce threading.Timer. Items still pending at process exit are lost"**（`deermem/core/queue.py:7`-`8`），理由是事实源（对话）在 checkpoint 里可重放，不值得为此上持久层（`:10`-`14`）。
- 优雅停机的补丁是 `MemoryManager.shutdown_flush(timeout)`：**有硬超时的 best-effort 排空**，返回 False 就丢弃尾巴——"strictly better than no flush"（`agents/memory/manager.py:401`-`426`），且超时必须对齐 K8s terminationGracePeriod，否则 SIGKILL 会把排水堵一半。
- watermark 是内容寻址的内存 LRU：**"a restart re-extracts one batch"**（`updater.py:865`-`867`）——丢 watermark 的代价被显式定为一个 batch 的重复提取，靠 fact 写入侧的幂等/去重兜住。
- 持久层只有两样：markdown facts（含 front matter 的 revision/confidence）与 `memory.json` 摘要；检索索引是可重建投影，adapter 失败标记 dirty 回退 substring。

staleness/eviction 的 `.metadata/` sidecar 是持久事实，但契约规定**不得**改动 canonical markdown 的时间戳/revision——即 sidecar 是"旁挂事实"，不反向污染主事实。

### 6. 子代理：注册表是内存 authority，证据是持久事实，图状态两者皆非

子代理线程池（见 [dual-threadpool-and-lifecycle.md](../concepts/subagent/dual-threadpool-and-lifecycle.md)）的三分法非常锋利：

- **注册表 `_background_tasks`/`_background_futures` 是进程级 dict**（`executor.py:357`-`361`）：轮询、取消、超时、清理全走它。Gateway 崩溃 → dict 没了 → 进行中的 task 无法恢复，ToolMessage 永不返回——父 run 由 run 侧 orphan 对账标 error。
- **子代理图 `checkpointer=False`**（`executor.py:1013`）：一次性执行、永不 resume，子代理的 ThreadState 从设计上就**不是持久事实**。checkpoint 坐标从父 ContextVar 继承只为流隔离（子帧进父的 subgraph namespace），不产生 checkpoint 写。
- **持久的事实是证据而非状态**：`task_*` 事件经 `_SubagentEventBuffer` 批量落 `run_events`（`subagent.start/step/end`），终端 token/模型名随 ToolMessage `additional_kwargs` 与 `subagent.end` 事件活过 reload；durable 批处理（`batch_task`）把 item/verdict 落表，靠 lease 认领实现跨崩溃重试——**要跨重启的子代理工作必须走 durable batch，不能走内存注册表**。

### 7. 配置双轨：restart-required 的事实 vs 运行时可写的事实

`config.yaml` 与 `extensions_config.json` 都是磁盘上的持久事实，但**可写性与消费时机**不同：

- `config.yaml`：运维手改；`STARTUP_ONLY_FIELDS` 逐字段声明"谁在启动时消费一次"（database/checkpointer/run_events/scheduler/sandbox/…，`config/reload_boundary.py:45`+，每条带原因文本）。热重载只覆盖非 startup-only 字段——**改了 `database.backend` 不重启，持久层还是旧的**。
- `extensions_config.json`：Gateway API 运行时可写；每次读-改-写持双锁（进程内 `extensions_config_write_lock` + sidecar advisory `extensions_config_file_lock`，`mcp.py:1190`、`skills.py:656`），因为单进程锁挡不住多 worker。原子写走 temp+rename，Linux 挂载点上 `EBUSY` 回退**非原子覆盖**——崩溃截断文件是这个持久事实的已知裂缝（backend/AGENTS.md 钉死）。

### 8. workspace / projects：磁盘即事实

上传、artifact、项目文档都是文件系统持久事实（内容地址、owner-scoped 目录，`config/paths.py:481`）。它们的"删除"是显式的生命周期操作（Gateway 删 thread 时 `delete_thread_dir`，`threads.py:618`；embedded client 无此路径）。没有投影层——文件本身就是 authority。

## 危险点清单：「写成投影却当 authority 用」及反之

逐条核验后的结论——**没有发现"投影被当 authority 消费"的正向违例**（delta 历史缓存、检索索引、accessor 图缓存都有严格的"纯性能、不进决策"契约），但存在以下六处**反向或边界危险点**：

1. **持久行冒充执行权（"写成事实却暗示 authority"）**：`runs.status=running` 是持久事实，但崩溃后它对"执行仍在进行"的暗示是假的——直到 orphan 对账跑过之前，REST 读到的 running 是**僵尸状态**。系统靠 lease 过期 + 心跳把窗口压到 grace 秒级，但没有 incarnation fence 消费者（见 6）。同理 `scheduled_task_runs.launching`。
2. **"持久事实"以配置为前提**：`database.backend=memory`（开发默认）与 `run_events.backend=memory`（默认）下，checkpoint、runs、事件 feed 全部退化为内存 authority——同一份代码，两种本体论。把开发默认当生产语义讨论恢复是常见误判。
3. **`threads_meta.incarnation` / `mcp_tasks.thread_incarnation`：写了持久事实却没有任何 authority 消费它**。digest 已核验：值被写入/复制（`thread_meta/sql.py:82`），但全仓没有等值比较或 fencing 调用点（[db-checkpointer-store-backends.md](../internals/persistence/db-checkpointer-store-backends.md) ThreadMetaRow 段）。它是为"防已准入写者在 thread 删除后复活"预留的 expand-phase 字段——**目前只是占位持久事实，不构成防复活机制**。事件 store 的 mutation fence 也自我声明"是序列化不是 incarnation fence"。
4. **extensions_config.json 的 EBUSY 回退写**：唯一的"持久事实写入路径可能在崩溃时撕裂"的点（非原子覆盖，backend/AGENTS.md）。配套测试钉住的是可写性而非崩溃原子性。
5. **内存队列/watermark 的丢失窗口是设计选择但有暗门**：`shutdown_flush` 只在优雅停机跑；OOM/panic 下未 flush 的提取 batch 静默丢失，watermark 重启后重复提取一个 batch 依赖写入侧幂等兜底——若后端 fact 去重配置漂移，重复提取会放大成重复 fact。
6. **`RunManager._runs` 的进程私有性**：它同时是准入互斥的 authority（同 thread 409）与状态视图；peer 的 store_only 复用行不进本表——任何绕过 RunManager 直接读 store 判断"是否有活 run"的代码会漏掉本地准入窗口，反之只读 `_runs` 会漏掉 peer 的活 run（`has_inflight` 只看本地记录，`manager.py:1947`-`1950`，跨 worker 互斥实际靠 `uq_runs_thread_active` 唯一索引兜底）。

## 统一恢复问题（审查清单）

审查 DeerFlow 里任何一个状态字段时：

1. 它落在 checkpointer/SQL 表/磁盘文件里的写入是否事务性（或原子替换）？
2. 它能否从 checkpoint 链、run_events 或文件**纯函数重算**？重算的 owner 是谁？
3. 当前哪个进程对象（RunManager、scheduler `_lease_owner`、journal、注册表、心跳任务）持有操作资格？
4. 重启后系统对它是**读回继续**（checkpoint）、**冷重算**（缓存/索引/feed 桥）、**重新授权**（lease/准入）、**标错对账**（runs/occurrences）、还是**静默丢失**（journal 缓冲/内存队列/watermark）？

只有第 1 问为真它才是跨进程事实；第 4 问的答案里"标错对账"和"静默丢失"是 DeerFlow 的默认恢复姿态——这与 DSH 的 pending/重新折叠风格形成对照：DeerFlow 宁可把在途工作标成 error 让用户重发，也不做执行态恢复。
