# 资源预算与公平性：并发、深度、总量与容量边界如何叠加

DeerFlow 的资源预算不是一个统一的"任务预算"，而是**六层各自独立的闸门**：run 级线程准入（reject/interrupt/rollback）、子代理响应级截断（SubagentLimitMiddleware）、进程级子代理执行容量（SubagentExecutionCapacity）、模型层进程内并发与 RPM 配速（llm_call / request_admission）、调度器全局 run 预算（scheduler），以及各基础设施 executor/semaphore 的小上限。一个典型请求的实际命运由**最先触发的那一层**决定，且各层的超限语义完全不同：有的排队（FIFO）、有的直接拒绝（ConflictError / AdmissionError）、有的静默截断（丢弃模型生成的多余 tool call）。

与 [dual-threadpool-and-lifecycle.md](../concepts/subagent/dual-threadpool-and-lifecycle.md) 的分工：那篇讲"子代理跑在哪个线程池/事件循环上、生命周期如何"；本文只讲"预算如何叠加、谁先触发、超限长什么样、公平性如何"。与 [01-run-manager.md](../internals/runtime/01-run-manager.md) 的分工：那篇讲 run 管理全貌；本文只取其准入策略一节做叠加链分析。

## 一、逐层核验：限制、默认值与配置键

### 1. run 级并发：同 thread 二选一，无排队

| 项 | 值 | 锚点 |
|---|---|---|
| 默认策略 | `multitask_strategy="reject"` | backend/packages/harness/deerflow/runtime/runs/manager.py:194、:613 |
| reject 语义 | 同 thread 已有 pending/running → 抛 `ConflictError`（"Thread … already has an active run"） | manager.py:1663-1665 |
| interrupt/rollback 语义 | 取消在途 run 后再创建；但若在途的是 checkpoint write（非 run）则拒绝 | manager.py:1657-1662 |
| 跨 worker 原子性 | store 层 `(thread_id) WHERE status IN ('pending','running')` 部分唯一索引 | manager.py:1592-1595（docstring） |

**没有 run 队列**：同 thread 的第二个请求要么被 409 拒绝，要么打断前一个。跨 thread 的 run 数量在 Gateway 层**无限制**（证据：manager.py 中只有 per-thread 准入检查，无全局 running 计数或信号量；全仓库 grep `Semaphore|max_concurrent` 也没有 run 级全局闸门）。这是一个重要发现：交互式 run 的全局并发上限实际上由下游（模型层、子代理容量）间接决定。

### 2. 响应级截断：SubagentLimitMiddleware（单响应并发 + 每 run 总量）

| 项 | 默认 | 配置键 / 范围 | 锚点 |
|---|---|---|---|
| 单响应并发 | 3（= `MAX_CONCURRENT_SUBAGENTS`） | runtime `max_concurrent_subagents`，夹在 [1,64] 且 ≤ `subagent_runtime.max_running` | backend/packages/harness/deerflow/agents/middlewares/subagent_limit_middleware.py:113；subagents/executor.py:1922；config/subagents_config.py:13、:26-36 |
| 每 run 总量 | 6 | `subagents.max_total_per_run`（schema 1-50；runtime override `max_total_subagents` 同夹紧） | config/subagents_config.py:11、:152-155；subagent_limit_middleware.py:110-116 |
| 超限行为 | 丢弃多余 `task` tool call（保留前 N 个），强制 `finish_reason=stop`，附加可见的 limit note；总量耗尽时 stamp `stop_reason="subagent_limit_capped"` | subagent_limit_middleware.py:145-173 |
| 计数口径 | 按 run_id 过滤 durable delegation ledger 去重计数；无 run_id 时**偏严**地计入全 thread 历史并告警 | subagent_limit_middleware.py:82-92、:142-144 |

关键点：这是**静默截断**而非拒绝——模型一个响应里生成 5 个 `task` call 而上限是 3 时，第 4、5 个直接从 AIMessage 的 tool_calls 里被删掉（subagent_limit_middleware.py:152-154），模型不会收到"被拒绝"的错误，只会看到截断后的提示文本。

### 3. 进程级子代理执行容量：SubagentExecutionCapacity

| 项 | 默认 | 范围 | 锚点 |
|---|---|---|---|
| `max_running` | 3 | 1-64 | backend/packages/harness/deerflow/config/subagent_runtime_config.py:11-16；config.example.yaml:1702 |
| `max_queued` | 64 | 0-10000 | subagent_runtime_config.py:17-22 |
| `admission_policy` | `"queue"` | queue/reject | subagent_runtime_config.py:23-26 |
| `queue_timeout_seconds` | 300 | 1-86400 | subagent_runtime_config.py:27-31；config.example.yaml:1705 |
| 失败形态 | 满且 reject（或队列 ≥ max_queued）→ `SubagentCapacityRejected`；排队超时 → `SubagentCapacityTimeout` | subagents/capacity.py:68-69、:90 |

公平性：**严格 FIFO**——waiters 是 `deque[asyncio.Future]`，release 时从队首转移 slot（capacity.py:43、:92-99）；排队者不占线程（capacity.py:37 类 docstring）。启动后**冻结**：活跃期间禁止重配置（capacity.py:150-155），换事件循环也要求完全空闲（capacity.py:169-177）。

与响应级的叠加：响应级 `max_concurrent` 解析为 `min(用户请求, startup max_running, 64)`（config/subagents_config.py:26-36），所以**响应级永远不会广播超过进程容量的并发**——两层不是重复，是 clamp 关系（详见 §二）。但注意：响应级限制的是"单条 AIMessage 里的 task call 数"，而进程容量限制的是"全 Gateway 同时执行的子代理数"——多个 run 各派 3 个时，第 4-… 个会在 capacity 层排队。

### 4. 嵌套深度：无深度计数器，靠工具剔除实现"深度 = 1"

- 内置 `general-purpose` 与 `bash` 子代理都带 `disallowed_tools=["task", "ask_clarification", "present_files"]`：backend/packages/harness/deerflow/subagents/builtins/general_purpose.py:67、bash_agent.py:47。
- system prompt 明说"You must NEVER attempt to call `task` or dispatch further subagents"：general_purpose.py:29-30。

**没有任何深度计数器或 max_depth 配置**（证据：全 subagents/ 目录 grep `depth|Depth` 只命中 middleware 链深度的注释，subagents/executor.py:1030、turn_budget.py:16，与委派深度无关）。深度限制完全由"子代理没有 task 工具"这个结构性事实保证——前提是 custom agent 的 `allowed_subagents` 配置没有重新暴露 `task`（AGENTS.md 声明 `[]` = hard deny，但这是配置责任，不是框架强制的深度计数）。与 DSH 的 `maxDepth` 计数器相比，这是一个不同的实现哲学：**能力剔除而非预算检查**。

### 5. durable batch（`batch_task`）：独立的三维预算

| 维度 | 默认 | 上限 | 锚点 |
|---|---|---|---|
| `max_items_per_batch` | 5000 | 100000 | backend/packages/harness/deerflow/config/subagent_batches_config.py:9 |
| `default_max_live_items` | 100 | 10000（且 ≤ max_live_items_per_batch=1000） | subagent_batches_config.py:10-11 |
| `default_max_running_items` | 3 | 64（per-batch 上限）；且 ≤ live | subagent_batches_config.py:12-13、:17-23（validator） |
| `max_attempts` | 3 | 10 | subagent_batches_config.py:14 |
| `max_result_chars` | 100000 | 1M | subagent_batches_config.py:15 |

batch 是显式工具选择，不消耗普通 run 的 ledger（subagents/AGENTS.md"Concurrency and total delegation cap"节）；其执行最终仍走同一个 `SubagentExecutionCapacity` 进程闸门。容量层拒绝/超时发生在模型执行之前，因此**不消耗 item 的重试预算**；真实执行失败和租约过期才消耗（同上 AGENTS.md）。

### 6. 模型层一：进程级 LLM 并发帽（默认关）

- 配置键 `llm_call.max_concurrent_calls`，**默认 0 = 不限制**（保留现状）：backend/packages/harness/deerflow/config/app_config.py:87-105；config.example.yaml:2872-2874。
- 实现是 `_ProcessWideLimiter`：基于 `threading` 原语（刻意不用 `asyncio.Semaphore`，因为它绑第一个事件循环，而 lead agent 主循环与子代理隔离循环必须共享一个帽）：agents/middlewares/llm_error_handling_middleware.py:129-200。
- 帽在**第一次中间件构造时冻结**（`_apply_configured_cap`），之后改配置无效，需重启：llm_error_handling_middleware.py:145-150、:348。
- 进程本地语义：多 worker 时聚合上限 ≈ `max_concurrent_calls × GATEWAY_WORKERS`（app_config.py:94-96 描述文字）。
- 等待者语义：permit 在 dequeue 时为该 waiter 预留（`granted=True`），取消后转交下一个——无损 FIFO 手递手（llm_error_handling_middleware.py:170-176）。

**默认无限制是重要发现**：开箱即用时，LLM 并发唯一的天然约束来自子代理容量（max_running=3）和 provider 自身的 429。

## 二、叠加链：lead agent 派 5 个子代理的完整限额穿越

以默认配置、`max_concurrent_subagents` 未覆盖（有效值 = min(请求, max_running=3, 64) = 3）为例：

```
用户消息
 └─> [闸1] Run 准入：同 thread 已有活跃 run？
        reject → ConflictError(409)，请求在此终结；无排队
 └─> [闸2] lead agent 模型调用（每轮）
        ├─ [闸2a] llm_call.max_concurrent_calls（默认 0=无限制，证据：app_config.py:87）
        └─ [闸2b] request_admission RPM（默认 None=无限制，证据：model_config.py:18）
             两者排队均为 FIFO；开启时 AdmissionError = 拒绝
 └─> [闸3] 模型生成 5 个 task tool call → SubagentLimitMiddleware.after_model：
        单响应并发 3 且 每 run 总量 6
        → 保留前 3 个，静默丢弃其余（+ limit note）     ← 截断，不是拒绝
 └─> [闸4] SubagentExecutionCapacity._acquire（进程级，跨 run 共享）：
        running < max_running(3)？ → 直接进
        否则 admission_policy=queue → FIFO deque 排队（不占线程）
             队满(≥64) 或 policy=reject → SubagentCapacityRejected  ← 拒绝
             排队 > 300s               → SubagentCapacityTimeout   ← 超时失败
 └─> [闸5] 子代理内部模型调用：再次穿过闸2a/2b（跨 loop 共享同一 limiter/
        limiter registry —— llm_error_handling_middleware.py:129-133）
 └─> [闸6] 子代理再派子代理：task 工具被 disallowed_tools 剔除
        → 结构性深度 = 1（无深度计数器，证据：§一.4）
 └─> [闸7] 沙箱：bash_command_timeout=600s / 子代理整体 timeout=1800s
 └─> 终局：stop_reason ∈ {token_capped, turn_capped, loop_capped,
        subagent_limit_capped, …}（加性字段，非新状态枚举）
```

谁先触发？**默认配置下闸 3 几乎总是先于闸 4**（响应级 clamp 到进程容量），闸 4 只在多 run 共享进程时才排队；闸 1 只在同 thread 重入时触发；闸 2 默认不设防。durable batch 路径则换成闸 4'（batch 三维预算）后再回到同一个闸 4。

## 三、公平性判定

| 队列 | 顺序 | 饿死可能 | 拒绝点 |
|---|---|---|---|
| SubagentExecutionCapacity waiters | 严格 FIFO（deque popleft 转移 slot） | 无饿死，但有**队头超时**：排 300s 不到 slot 即失败（capacity.py:74-90） | 满且 reject / 队满 → Rejected |
| request_admission waiters | FIFO ticket，且"队首才能通过"（`self._waiters[0] is not ticket` 挡插队） | 无饿死，deadline 300s（默认）兜底 | 队满 256 / 超时 → AdmissionError |
| _ProcessWideLimiter waiters | FIFO + permit 预留转交，取消不泄漏 | 无饿死 | 默认无限制（cap=0） |
| scheduler 持久队列 | 同 thread FIFO；跨 task 由 claim 顺序决定 | `min_once_delay_seconds=60`（scheduler_config.py:11）限 once 重排；queue_timeout 3600s 防无限等待 | 预算满 → 留队不拒绝 |
| run 准入 | **无队列** | 不适用 | 同 thread 活跃 → ConflictError |
| 响应级 task 截断 | "保留前 N 个" = 模型生成顺序，无优先级概念 | 不适用 | 静默截断 |

跨层没有全局公平调度器：子代理容量按"谁先 _acquire"服务（多 run 混序），scheduler 预算按 DB 声明顺序。但每一层内部都是 FIFO + 有界等待，不存在无界排队或优先级倒置。

## 四、不理想化清单（"无限制"本身是发现）

1. **run 全局并发无限制**：Gateway 不限制跨 thread 的同时 run 数（§一.1）。
2. **LLM 并发默认无限制**：`llm_call.max_concurrent_calls=0`（§一.6），文档自己承认需要配 nginx `limit_req` 才有集群级意义。
3. **RPM 配速默认关闭**：`request_admission=None`（§一.7）。
4. **嵌套深度无计数器**：深度=1 靠工具剔除，custom agent 配置疏漏时框架不设第二道深度闸（§一.4）。
5. **每 run 总量上限宽松区间**：schema 允许放到 50，默认 6；截断是静默的，模型侧只有一条可见提示。
6. **子代理容量重配置被禁但只在启动快照生效**：热改 `subagent_runtime.max_running` 对已创建的 controller 无效（capacity.py:150-155；reload_boundary.py 将其列为 startup-only）。
