# DeerFlow 应用开发模型：owner、证据与交付判断

## 这卷解决什么问题

新建独立 DeerFlow 应用仓后，最容易出现的不是不会写入口代码，而是不知道怎样把用户意图、接入形态、实现、配置组合、测试资产和交付判断连成一条可复查的链。本卷给出一张 DeerFlow-native 的总地图：哪些事实由谁拥有，哪种验证能证明什么，以及为什么"能 import"、"测试绿"、"扩展装上了"、"用户验收"是四件不同的事。

这是一种将依据 DeerFlow v2.1.0 源码、文档、指南与示例归纳出的开发模型，不是 DeerFlow 官方宣布的方法名，也不是应用仓必须复制的主仓库制度。本卷正文逐页区分四类陈述：DeerFlow 运行时事实、DeerFlow 主仓要求、应用仓建议、仓库自定。本页先给框架；各页的证据锚点（钉定 v2.1.0 的链接与行号）在正文页建立时逐条落地。

## 一页总览：四个层次不要混成一件事

独立应用开发同时面对四个层次。运行时接口回答"你的代码怎样被 DeerFlow 装载与调用"；仓库结构回答"源码、测试、文档放在哪里"；分发形态回答"用户或部署者拿到什么、怎么装"；治理规则回答"谁评审、哪些检查必须通过、什么条件允许发布"。DeerFlow 的文档与契约主要定义运行时接口和可用组合机制；应用仓需要为自己的仓库结构、分发形态和治理规则指定 owner。

| 层次 | 主要问题 | DeerFlow 能直接提供什么 | 应用仓仍需自己决定什么 |
|---|---|---|---|
| 运行时接口 | 入口点怎样被发现？贡献怎样进组合？资源怎样清理？ | extension 入口点与贡献类型、skill 格式与发现、MCP 配置、嵌入式 client（取证中） | 应用自己的接口、事件、配置与错误合同 |
| 仓库结构 | 源码、测试、文档、构建产物放在哪里？ | 示例扩展的包结构范例 | 独立仓、monorepo、workspace 边界 |
| 分发形态 | 用户安装什么？ | extension 安装事务、skill 目录、依赖引入（取证中） | 发布物、自包含要求、兼容范围与升级路径 |
| 治理规则 | 谁评审、哪些检查是门槛、怎样决定发布？ | 主仓规则可作为参考（见 SDLC 参考卷） | 自己的 issue、review、CI、release 与安全审批 |

**能被加载 ≠ 有行为证据 ≠ 能被安装 ≠ 已获验收。**这四个结果必须分别被观察和记录；本卷的核心任务就是把每一层"由什么证据证明"讲清楚。

## 开发闭环（本卷的组织骨架）

正文页将沿这条闭环展开，每一环对照 v2.1.0 的实际机制取证：

1. **先定义外部结果**——从用户能观察到的结果开始，而不是从"我要改哪个文件"开始；
2. **选择接入形态并找到事实 owner**——四种形态（extension 包 / skill / MCP / 内嵌 client）各适合什么，每类事实的权威维护位置在哪；
3. **形成完整的垂直切片**——实现、用户文档、配置消费者、行为证据与必要的决定记录一起交付；
4. **让测试观察真实对象**——每个测试层只证明它实际断言的属性；mock 与真实组合各有边界；
5. **验证用户实际安装的形态**——源码能跑不等于分发物能装；
6. **用证据完成交付判断**——机器检查、语义评审与用户验收回答不同问题。

## 最重要的注意事项（预告）

正文页将逐条展开，先立标题为戒：

- 不要把"能 import"当作行为证据；
- 不要只做 mock-only 测试就声称组合成立；
- 不要把"扩展管理器装上了"当作用户验收；
- 不要把 DeerFlow 主仓的 SDLC 制度当成随依赖继承的义务。
