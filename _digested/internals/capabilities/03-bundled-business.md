# Bundled business 集成 — 自带 HTTP 客户端的三个 MCP provider

`deerflow/capabilities/business.py` 是这个目录里唯一**真的会发网络请求**的模块。它的定位在首行写死（`business.py:1`）：*"Bundled business tools served through the existing stdio MCP lifecycle."*——不是新服务、不是新的工具运行时，而是**给既有 stdio MCP 通道喂一个由 DeerFlow 自带的 server 进程**。

选这三个 provider 的理由写在 `docs/capability-center.md`：它们此前要么需要用户自己找第三方 MCP server，要么根本无法通过 plug-in 安装（本仓库的 IM 通道是**收消息**方向，不能拿来主动发群通知）。实现是照 provider 契约独立写的，Dify 的插件只影响了功能范围（`docs/capability-center.md` 原文）。

## 相关文件

- `deerflow/capabilities/business.py`（178 行）— `CREDENTIALS` / 供应商默认端点表 / `connection_config` / `is_bundled_connection` / `BusinessClient` / `build_server` / `main`
- `deerflow/capabilities/builtin.json` — 三条 `adapter: "business"` 的清单：dingtalk（`:42`）、wecom（`:99`）、hubspot（`:531`）
- `app/gateway/capabilities.py:156-171` — `BusinessAdapter`：把清单 `config_schema` 的凭据字段交给 `connection_config()` 生成 launcher
- `app/gateway/routers/mcp.py:778-837` — `_validate_mcp_update_request()`：stdio 执行白名单，`is_bundled_connection` 是其中唯一例外
- `app/gateway/routers/personal_mcp.py:47-62` — `_validate_personal_server()`：普通用户被允许的唯一 stdio 形态
- `backend/tests/test_business_plugins.py`（168 行）— wire 契约、错误不泄密、真实 stdio 调用的测试

## 1. 三个 provider 的静态事实

| provider | 供应商默认端点表 | 凭据键（`CREDENTIALS`） | 暴露的工具 | 清单 `version` |
|----------|----------------|--------------------------|------------|-----------------|
| `dingtalk` | `https://oapi.dingtalk.com`（`business.py:15`） | `access_token`、`sign_secret` | `send_message(content, message_type, title)` | `"2"` |
| `wecom` | `https://qyapi.weixin.qq.com`（`business.py:16`） | `webhook_key` | `send_message(content, message_type, title)` | `"2"` |
| `hubspot` | `https://api.hubapi.com`（`business.py:17`） | `access_token` | `get_companies(limit, after)`、`create_contact(...)` | `"2"` |

`CREDENTIALS` 是 `dict[str, tuple[str, ...]]`（`business.py:24-28`）——**键集合就是白名单**：不在表里的 provider 一律 `ValueError`，多给一个凭据键也一律 `ValueError`。这把"用户配置的自由度"收窄到"只能填这几个已知字段"，与清单 `config_schema` 的字段名**逐一对应**（dingtalk 的 `config_schema` required 是 `name`/`access_token`/`sign_secret`，`builtin.json:90-94`；wecom 是 `name`/`webhook_key`，`:143-147`）。`name` 是连接显示名，不属于 provider 凭据，因此在进 `connection_config()` 之前被前端剥掉（`plugin-adapters.tsx:36-39`）。

`version: "2"` 与其它条目（多为 `"1"`）不同——清单版本变了，`PluginManifest.version` 会随安装写进 `capability.version`（`app/gateway/capabilities.py:143`），但**不参与 identity**（[02](02-installation-identity-and-agent-selection.md) §1）。

## 2. `connection_config()`：凭据不落盘，只落 env

`connection_config(provider, values)`（`business.py:31-56`）返回一个**完整的 stdio MCP server 配置**：

- `command` = `sys.executable`
- `args` = `["-I", "-m", "deerflow.capabilities.business", provider]`
- `env` = 三个以固定 provider 前缀加凭据键名构造的环境变量（`business.py:20` 的前缀常量定义 + `:44-46` 的 `setdefault` 默认 URL）

关键点：**凭据只以 env 形式存在**，不出现在 `command`/`args`、不出现在 tool `inputSchema`、不出现在错误信息里。`test_business_plugins.py:74-80` 断言 `build_server("hubspot").list_tools()` 在**没有任何凭据**时也能发现两个工具，且 schema 里不含 `access_token`——发现阶段不需要凭据。

`connection_config()` 的校验顺序（`business.py:35-42`）：provider 不在 `CREDENTIALS` → `ValueError`；任一必需键缺失或空白 → `ValueError`；值等于掩码占位符 `***` → `ValueError`（防止把 GET 掩码值回写成真凭据）；`hubspot` 额外要求显式 `url` 通过 `validate_public_http_url()`。`test_business_plugins.py:83-86` 的四组参数就是这四条。

## 3. `is_bundled_connection()`：执行白名单里唯一的窄例外

这是本模块**最重要**的一处，因为它直接决定了一个普通用户能不能让 Gateway 起一个本地进程。

`_validate_mcp_update_request()`（`routers/mcp.py:778-837`）是 API 侧 stdio 的闸门：默认允许的启动器只有 `npx` / `uvx`（`routers/mcp.py:52`，可用 `DEER_FLOW_MCP_STDIO_COMMAND_ALLOWLIST` 扩展，`:674-681`），还要过集群式 exec flag 检查（`:825-830`）与代码注入环境变量检查（`:832-837`）。`is_bundled_connection()` 是**这三个检查之前的前置短路**：

```python
if is_bundled_connection(server.command, server.args, server.env):
    continue                                    # routers/mcp.py:804-805，整条 server 跳过所有检查
if enforce_execution_policy and is_bundled_connection(sys.executable, server.args, server.env):
    raise HTTPException(400, "Bundled MCP server '{name}' uses a different Python interpreter. …")   # :806-815
```

第一条注释（`routers/mcp.py:802-803`）：*"This exact isolated interpreter/module/provider tuple is generated by our bundled adapter, never an arbitrary API-supplied executable path."*

因此 `is_bundled_connection(command, args, env)` 必须是**逐项精确匹配**，不能是前缀/后缀判断。它能接受的元组是：

1. `command` 等于 `sys.executable`；
2. `args` 是 `["-I", "-m", "deerflow.capabilities.business", <CREDENTIALS 内的 provider>]`；
3. `env` 的键集合不超出该 provider 的凭据键集合（同一前缀 + `CREDENTIALS` 键名）。

> 未逐行核实：`is_bundled_connection()` 与本页 `business.py:NN` 行号引用（该模块采用压缩排版，本次未逐行展开）——本页结论来自它的三个调用点与 `docs/capability-center.md` 的描述（*"An exact `sys.executable -I -m deerflow.capabilities.business <provider>` launcher with only the provider's known credential environment keys is accepted by the MCP API; arbitrary interpreter paths/modules/flags/environment remain rejected."*）。

### 为什么个人态也允许它

`_validate_personal_server()`（`personal_mcp.py:47-62`）对**非管理员**的规则是"只能 HTTP/SSE 公网端点，不能有 OAuth"，唯一例外：

```python
bundled = server.type == "stdio" and is_bundled_connection(server.command, server.args, server.env) and not cwd
if (server.type not in {"http", "sse"} and not bundled) or server.oauth is not None:
    raise HTTPException(403, "Only an administrator may configure host commands or OAuth token endpoints")   # :56-57
```

`and not cwd` 是一条独立约束：**带上 `cwd` 就不再算 bundled**，因为 `cwd` 能让一个"固定模块"在任意目录下解析出别的 `deerflow` 包（`personal_mcp.py:53` 注释：*"The response model does not declare `cwd`; a supplied one is an extra."*）。

即便放行，后续仍会继续 `mcp._validate_mcp_update_request(...)`（`personal_mcp.py:62`）——bundled 元组之外的一切照旧过白名单。

### 版本迁移时的定向报错

部署环境迁移 Python 后，老连接里的 `sys.executable` 陈旧，第一条短路失效、第二条命中，返回的不是笼统的"命令不允许"，而是**带上当前解释器路径的可操作错误**，并明确告知"保留 capability 元数据与凭据、不要删除重装"（`routers/mcp.py:809-814`）——因为删除重装会换掉 installation ID，从而静默解绑 Agent 的选择（[02](02-installation-identity-and-agent-selection.md) §1 性质 4）。

## 4. `build_server()`：工具面与注解

`build_server(provider)`（`business.py:59`）返回一个 `Server`，`main()`（`:171-174`）用 `parser.parse_args().provider` 决定 provider，所以**一个进程只服务一个 provider**。

工具注解是这些工具"像不像安全操作"的唯一信号，写在 `@server.tool(annotations=ToolAnnotations(...))` 上：

| provider / 工具 | `readOnlyHint` | 其他 annotation | 说明 |
|-----------------|-----------------|------------------|------|
| robot 的 `send_message` 分支 | `False` | `destructiveHint=False`、`openWorldHint=True` | 对外发消息，不可只读；文档明确"不要在投递不确定时自动重试" |
| hubspot `get_companies` | `True`（`test_business_plugins.py:80` 断言） | — | 纯读 |
| hubspot `create_contact` | `False` | — | 写 |

`test_business_plugins.py:80` 用 `tool.annotations.readOnlyHint == (tool.name == "get_companies")` 一句门定住这个不变量。

> 未逐行核实：`build_server()` 内按 `provider` 分支的完整行号（`:61-168` 区间），本页只核对了 robot 的 `send_message` 注解 `business.py:163-166` 与 HubSpot 两个工具的发现行为。

## 5. `BusinessClient`：失败策略

`BusinessClient(provider, credentials, http)`（`business.py` 内，`test_business_plugins.py:27` 的构造方式）把**传输**留给调用方注入的 `httpx.AsyncClient`，这也是测试能用 `MockTransport` 而不发真请求的原因。

失败策略来自 `docs/capability-center.md` 的原文与测试的共同约束：

| 规则 | 证据 |
|------|------|
| **HTTP 200 也要查业务码**：机器人返回 `errcode != 0` 视为失败 | `test_business_plugins.py:43-49`（200 + `errcode: 40014` → `ValueError`）；`:157-167`（群机器人缺业务状态字段 → 失败） |
| **错误里绝不出现 provider 响应体或含凭据的 URL** | `:49` 与 `:168` 断言 `"secret-token"` / `"super-secret"` 不在异常文本中；`:157-162` 用一个 `ConnectError("https://example.test?key=super-secret")` 制造"异常消息本身带凭据"的 worst case |
| **不跟随重定向**：302 直接失败 | `:43` 的参数化包含 `(302, {})` |
| **不自动重试写操作** | `docs/capability-center.md`："no redirect following or automatic write retries"；机器人工具 docstring 亦写 "Do not automatically retry uncertain delivery."（`business.py:165`） |
| **固定 provider 端点，不接受用户任意 host** | 供应商默认端点表（`business.py:15-17`）；`hubspot` 若显式给 `url` 必须过 `validate_public_http_url()`（`:40-42`） |
| 超时 / 响应体大小有界 | `docs/capability-center.md`："bounded responses and timeouts"；具体数值**未逐行核实** |

wire 形态由 `test_robot_wire_contract`（`:19-39`）钉死：dingtalk 走 `?access_token=…&timestamp=…&sign=…`，body 是 `{"msgtype": "markdown", "markdown": {"text": …, "title": …}}`；wecom 走 `?key=…`，body 是 `{"msgtype": "markdown", "markdown": {"content": …}}`。HubSpot 用 `Authorization: Bearer <token>`，分页参数是 `after` + `limit`（`:66-68`）。

## 6. 凭据如何穿过 subprocess 的 env 白名单

这条链容易被误读，逐段写清：

1. `connection_config()` 把凭据放进 server 定义的 `env`（`business.py:44-46` 附近）。该 `env` 会被**持久化**进 `extensions_config.json`（部署态）或个人 `mcp.json`（个人态），因此 GET API 必须掩码（`routers/mcp.py:846-847`），回写时必须拒绝掩码占位符（`_ensure_no_masked_secrets()`，`routers/mcp.py:590-607`）。
2. `McpServerConfig.env`（`extensions_config.py:226`）在客户端构参时被塞进 `params["env"]`（`mcp/client.py:32-34`）。
3. 每次 stdio 调用前，harness 在**不覆盖**已有 env 的前提下补 `TMPDIR`/`TMP`/`TEMP`（`mcp/tools.py:728-732`，注释："Merge rather than replace any operator-provided env."）。
4. 真正决定子进程环境的是 `mcp` SDK：它先取 `get_default_environment()`——POSIX 下只继承 `HOME/LOGNAME/PATH/SHELL/TERM/USER`（`backend/.venv/lib/python3.12/site-packages/mcp/client/stdio/__init__.py:28-45`）——再叠加 server 的 `env`。

所以 **server 的 `env` 不是"extra"，而是子进程拿到凭据的唯一途径**；而 host 环境里的其它变量（比如宿主机 shell 里 export 的任意密钥）不会自动漏进子进程。`-I`（isolated 模式）再掐掉当前目录与用户 site-packages 对 `sys.path` 的影响，保证 `-m deerflow.capabilities.business` 解析到的是部署安装的那份代码。

> 第 4 步的三方版本锁定：上面引用的是本 worktree 里 `backend/.venv` 实际安装的 `mcp` 包源码，不是仓库代码；升级 `mcp` 依赖时该白名单可能变化。

## 7. 边界（这段很短的清单值得先读）

- **业务方向单一**：三个 provider 都只做**对外主动写/读**（发群通知、查/建 CRM）。它们**不接入** DeerFlow 的 IM 收消息通道，不读聊天记录、文档或日历——`builtin.json` 里 dingtalk/wecom 的 `setup` 文案原文就写了"此插件不读取聊天、文档或日历"。
- **保存配置不等于验证**：`docs/capability-center.md`："Configuration saves credentials without sending a message or creating a CRM record."；`health` 在发现接口里恒为 `unknown`（[01](01-catalog-and-adapters.md) §3.3）。
- **不重写既有手工配置**：清单版本变化不会改写已存在的 CLI/手工连接（`docs/capability-center.md`："Existing manually configured CLI connections are not rewritten when the catalog entry changes."）。
- **删除重装会换 identity** → 解绑 Agent 选择；修解释器路径请就地编辑 `command`。
- 与执行期的关系同 [02](02-installation-identity-and-agent-selection.md) §6：本模块只提供"一个被允许启动的固定 server"，工具被调用后仍走 MCP 拦截器链与工具级风险门（[../../enterprise-operations/security/03-guardrail.md](../../enterprise-operations/security/03-guardrail.md)）。
