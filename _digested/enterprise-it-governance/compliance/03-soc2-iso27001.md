# SOC 2 / ISO 27001 对照

> ⚠️ **本页不构成合规结论**。以下只描述「有没有对应技术机制」，
> 不判定任何系统是否满足 SOC 2 或 ISO 27001，也不替代审计意见。

## 1. 两类控制的分界

这两套标准都同时要求**技术控制**与**组织控制**。DeerFlow 只能提供前者。

| 类别 | 谁能提供 | 例子 |
|---|---|---|
| **技术控制** | 软件 | 访问控制、审计日志、加密、隔离 |
| **组织控制** | 部署方 | 权限审批流程、员工培训、供应商评估、事件响应预案、业务连续性计划 |

**这一步划分决定了本页的价值**：翻遍源码也找不到「员工背景调查」的实现，
那不是缺陷，是软件与组织的分工。

## 2. 访问控制（CC6）

| 能力 | 状态 | 证据 |
|---|---|---|
| 身份认证 | 有，四条路径 | [../identity/01-authentication-model.md](../identity/01-authentication-model.md) |
| SSO / OIDC | 有 | [../identity/07-sso-and-oidc.md](../identity/07-sso-and-oidc.md) |
| RBAC | 有，13 个权限 | [../authorization/04-rbac-permissions.md](../authorization/04-rbac-permissions.md) |
| 用户隔离 | 有，per-user 目录 | [../identity/03-user-isolation.md](../identity/03-user-isolation.md) |
| 登录限速 | 有，可配 | [../identity/09-login-throttle.md](../identity/09-login-throttle.md) |
| 最小权限默认 | **否** | `app/gateway/authz.py:288-290` —— 未启用时返回**全部**权限 |
| 定期权限复核 | **无** | 无「导出当前权限分配」的报告 |
| 离职即时撤权 | **是** | `disabled` 在每次 JWT 请求检查（`deps.py:1396-1411`）；PAT 每次查 disabled（`pat.py:229-233`） |

### 2.1 最小权限的默认值

`app/gateway/authz.py:288-290`：

```python
if config.enabled is not True:
    return list(_ALL_PERMISSIONS)
```

**授权关闭时返回全部权限**——这是"legacy all-permissions behavior"（`app/gateway/authz.py:281`）。
所以「最小权限」这件事**必须显式开启授权**才成立。

### 2.2 撤权的传播

| 层 | 撤权是否立即生效 |
|---|---|
| PAT | 是（每次请求查库，`app/gateway/auth/pat.py:229-233`） |
| 内部 owner 头 | 是（每请求查 users 表，`app/gateway/auth_middleware.py:129-136`） |
| session / JWT | **是**——每次 JWT 验证检查 `token_version` 与 `disabled`（`deps.py:1396-1411`） |

所以停用账号（`disabled`）就能在**下一次请求**阻断 JWT 与 PAT；
`token_version` +1 是改密场景的额外作废手段，不是停用的必需步骤。

## 3. 审计日志（CC7）

| 能力 | 状态 | 证据 |
|---|---|---|
| RunJournal（中间件决策） | 有 | [../audit/01-audit-chain.md](../audit/01-audit-chain.md) |
| Sandbox 审计 | 有 | [../audit/03-sandbox-audit.md](../audit/03-sandbox-audit.md) |
| 登录/认证事件 | 部分 | 有日志，非结构化事件 |
| 日志防篡改 | **无** | 无签名链、无只追加存储 |
| 日志导出给 SIEM | **无原生支持** | 需自行采集文件或库 |
| 日志保留策略 | **无** | 依赖外部日志系统 |

**「防篡改」这一条值得单独说**：SOC 2 与 ISO 27001 都关注日志完整性。
DeerFlow 的 journal 存在关系库里，有库访问权的人可以改写它。
没有哈希链或写入即不可变的机制。

## 4. 变更管理（CC8）

| 能力 | 状态 | 说明 |
|---|---|---|
| 配置版本控制 | **仓库自定** | `config.yaml` 是 gitignored 文件，版本控制靠部署方 |
| 配置热更新 | 部分 | 部分键支持热读，部分需重启 |
| 配置变更审计 | **无** | 改 `config.yaml` 不产生事件 |
| 代码版本 | 有 | git 仓库 |
| 迁移可追溯 | 有 | 51 个 migration 文件按序可查 |

**关键事实**：`config.yaml` 与 `extensions_config.json` 都是**gitignored** 的
（见 `AGENTS.md` 的 Repository Map 说明），因此**框架本身不提供配置变更历史**。
要满足变更管理，需要部署方把这两个文件纳入自己的版本管理。

### 4.1 重启需求的不一致

部分配置改动需要重启，部分不需要。以登录限速为例：
`config.example.yaml:3546-3555` 说明若干键是 live-read，
而 `:3558` 标注另一些需要重启。

**这不是缺陷，但意味着「改配置」不能假设立即生效**——评审时会问「你怎么知道生效了」。

## 5. 风险评估（CC3 / ISO 27005）

| 能力 | 状态 |
|---|---|
| 沙箱隔离（降风险的技术手段） | 有 |
| Guardrail（策略执行） | 有 |
| 循环检测（资源风险） | 有 |
| **风险登记簿** | **无**——文档性产物 |
| **风险评估方法** | **无**——组织流程 |

框架提供的是**风险缓解的手段**，不是**风险管理的流程**。

## 6. 供应商管理（CC9）

DeerFlow 本身不调用固定的外部服务，但**部署后必然引入第三方依赖**：

| 依赖 | 谁选择 |
|---|---|
| LLM provider | 运营方（`config.yaml`） |
| 搜索/抓取 API | 运营方 |
| TypeSafe API（memory-extraction） | 功能开关 |
| IM 平台 | 运营方 |
| personal MCP | **用户** |

**没有供应商登记表或供应商评估输入**。这一项完全落在组织侧。

唯一值得框架层面记录的是 **`personal MCP` 让用户能引入未经评估的第三方**——
这条与供应商管理原则直接冲突，且框架层无法限制
（见 [../authorization/05-mcp-scope.md](../authorization/05-mcp-scope.md) §6）。

## 7. 缺口汇总

| 缺口 | 状态 | 边界 |
|---|---|---|
| 最小权限默认 | **否** | 授权关闭 = 全部权限 |
| 权限分配报告 | **无** | 无导出端点 |
| 日志防篡改 | **无** | 库内可改写 |
| 配置变更审计 | **无** | 改 `config.yaml` 无事件 |
| 配置版本控制 | **仓库自定** | 文件 gitignored |
| SIEM 原生导出 | **无** | 需自建采集 |
| 日志保留策略 | **无** | 依赖外部 |
| 风险登记 / 供应商登记 | **无** | 组织侧产物 |
